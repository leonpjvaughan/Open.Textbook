# One repository for the solvers

> **Decided, 2026-10-26.** The four questions at the end were answered and the work
> followed: no `git subtree` (a plain copy; the history stays in the archived repo),
> `open_textbook.otkd` with `solvers/otkd`, all seven kernels with a figure each, and
> the version from the collection tag through `hatch-vcs` rather than a frozen number.
> The record below is the proposal as written; `DECISIONS.md` is the decision.

**Dated:** 2026-10-26. **State:** proposal. Nothing here is built, and nothing is
approved. The measurements are from this machine on this date; the commands are
named so they can be repeated.

This is the record of a decision that touches three things at once:

1. a new `solvers/` directory holding a Rust package, `ot-solve`, for the kernels a
   page runs in the browser;
2. moving the `suspension-kinematics` repository (`otkd`) into this one and
   archiving it;
3. whether the collection should publish under an `open-textbook` namespace.

They are one decision because they answer one question: **where does the code that
computes a page's numbers live, and how does its output get into a page?**

## What exists, measured

| | |
|---|---|
| `otkd` | 0.11.0 (installed dev build `0.11.1.dev2+gd59535ece`), 99 tracked files, 1.3 MB, 110 tests, MIT |
| its bundle | 3.5 MB, six models, six compiled kernels (623 KB of wasm), vendored at `books/maths-applied/docs/assets/data/otkd/` |
| how it arrives | `scripts/vendor-otkd.sh` downloads a GitHub release zip pinned by version **and** sha256; `--check` verifies the committed tree offline |
| what CI does | **nothing that compiles it.** `.github/AGENTS.md`: "CI installs no compiler for a vendored binary … never a job here" |
| the browser side | the generated `kernel.js` inlines the wasm as base64; a figure imports it; `WebAssembly.instantiate` runs on load |
| service worker | keeps only content-addressed assets across a deploy. `assets/data/` is not addressed, so it lives in the runtime cache, which `activate` deletes |
| a std Rust kernel | `sqrt` + `sin` + `exp` + `ln_1p` compiles to **8.9 kB** wasm (**4.0 kB** gzip) |
| reproducibility | the same source built in two different directories produced **byte-identical** wasm (64 B and 8.9 kB test kernels, `rustc 1.99.1`, `-O -C panic=abort -C strip=symbols -C lto=fat`) |
| the cost of otkd's tests | 21 tests took **2m15s**; the suite is 110 tests. A full bundle rebuild was still building models after several minutes |

Two of those numbers decide most of what follows. **The wasm is small** — a kernel is
a rounding error beside a figure module, so a shared bundle costs nothing. **The
otkd suite is slow** — 21 of its tests take 2m15s, which extrapolates to about
twelve minutes for the 110. The move must not put otkd on the default path.

## Recommendation

**One repository, one `solvers/` tree, two producers, one ABI, and a CI job that
rebuilds the wasm to compare it with the committed bytes.**

```
solvers/
├── AGENTS.md                 # the rules for this tree
├── ABI.md                    # the contract, versioned
├── Cargo.toml                # workspace: ot-solve, ot-solve-build
├── Cargo.lock
├── rust-toolchain.toml       # the channel and the wasm target, pinned
├── ot-solve/                 # Rust library: the hand-written numerical kernels
│   ├── src/
│   │   ├── lib.rs            # the registry and the exported symbols
│   │   ├── abi.rs            # blocks, statuses, the layout hash
│   │   ├── grid.rs           # 1-D grid, boundary conditions, stencils
│   │   ├── linalg.rs         # tridiagonal solve, matvec, CG
│   │   └── kernels/          # one module per kernel, behind a feature
│   └── tests/                # the maths, against known solutions
├── ot-solve-build/           # Rust binary: manifest, selftest, JS module, sums
└── otkd/                     # Python: the mechanism compiler, moved here
    ├── pyproject.toml        # its own project and uv.lock, not a root member
    ├── src/otkd/…
    ├── tests/…
    └── docs/…                # the design record comes with it
```

Why one tree for two languages: `ot-solve` and `otkd` are the two ways a kernel is
produced — hand-written numerical methods, and a kernel generated from a symbolic
derivation. The page should not know which. They share an ABI, a loader, a build
script and a repository release, and they are read together when a page needs a new
one.

**"src layout" in Rust is `ot-solve/src/`.** Cargo fixes the crate root at the
package's `src/`, so a Python-style `solvers/src/ot_solve/` would need a `path`
override on every target and would confuse `cargo` tooling, editors and
`rust-analyzer`. The thing the request is asking for — one package directory whose
shipped code is under `src/`, tests outside it, nothing to filter at copy time — is
what the tree above does.

Rejected:

- **Keep otkd separate and keep vendoring a release zip.** That is the two-repo
  version dance the question exists to remove: a model changes, a tag is pushed, a
  zip is downloaded, a digest is pasted into a script, and nothing checks that the
  bytes in the repo are the source in the other repo.
- **A git submodule.** A clone could no longer build from the bytes it has.
- **A second repository for ot-solve.** Two release trains for one consumer.
- **A published `ot-solve` crate.** Nothing outside this repository consumes it, and
  publication turns the ABI into a public promise before it has been used twice.

## The ABI: how it stays general

The generality is not in the number of kernels. It is in **a contract small enough
to keep, and specific enough that a new kernel needs no new browser code**.

Ten rules, and each is a decision:

1. **A kernel knows nothing about the book.** No DOM, no units, no prose, no
   book-specific constants. Numbers in, numbers out. The manifest carries the
   *names* of the numbers; a figure decides which of them to show.
2. **A fixed arena, a declared layout.** No allocator and no growth. Capacity is
   compile-time; the used size is a parameter. The arena is a flat `f64` array cut
   into named blocks — `params`, `state`, `out`, `diag` — and the offsets come from
   one Rust table, not from arithmetic repeated in JavaScript.
3. **Three calls, not thirty.** `init`, `step`, `run`. A time-dependent kernel is a
   frame at a time, so a scrubber can advance it without re-allocating; a steady
   kernel is one `run`. Everything else is a block in the arena.
4. **Status, not traps.** `0 ok`, `1 unstable`, `2 not converged`,
   `3 bad parameter`, `4 not initialised`. A heat scheme pushed past `r = 1/2` must
   *report* that it is growing, so the figure can draw the growth; a trap gives the
   reader an empty rectangle and the console a stack trace.
5. **Deterministic.** No clock, no unseeded randomness, no threads. The same params
   produce the same bits, and the build records a vector that proves it.
6. **One artifact per kernel.** A page downloads only what it mounts. A kernel's ABI
   can move without moving every other kernel.
7. **The manifest is generated, never written.** Parameters (name, label, default,
   range, step, unit), outputs (block, offset, length, unit), capacity and the
   layout hash all come from the Rust declaration. The controls a figure builds and
   the wasm that reads them cannot disagree, because one table produced both.
8. **The loader is hand-written and shared.** The generated module is data: a
   manifest and the wasm as a string. The logic that checks the ABI, maps the
   blocks and reads a status lives once, in `assets/figures/kernel.js`, and is
   tested once.
9. **Two producers, one contract.** `otkd` keeps its current `otkd-kernel-2` until
   the shared ABI has been used by `ot-solve` in a page; then it moves once, with a
   version bump. No page mixes the two in one figure before then.
10. **Prove the artifact.** A selftest vector is generated by running the kernel
    natively at build time and is replayed against the wasm in Node. It catches the
    failures that a Rust unit test cannot: a stale artifact, a wrong offset, a
    wrong endianness, a broken base64, a shim bug.

### The exported surface

| export | signature | meaning |
|---|---|---|
| `abi` | `() -> i32` | calling-convention version; the loader refuses a mismatch |
| `arena` | `() -> i32` | byte offset of the f64 arena in linear memory |
| `slots` | `() -> i32` | how many `f64` the arena holds |
| `layout` | `() -> i32` | FNV-1a of the block table; the loader compares it with the manifest |
| `init` | `() -> i32` | validate the params and reset the state from the caller's initial data |
| `step` | `() -> i32` | advance one step |
| `run` | `(i32) -> i32` | advance at most `n` steps, stopping on the first non-zero status |
| `memory` | `Memory` | the linear memory the views are made from |

That is the whole surface: seven functions and one memory. A kernel that needs
something else has outgrown the ABI, and that is a design conversation rather than
an extra export.

### What a kernel looks like

```rust
// solvers/ot-solve/src/kernels/heat.rs
pub const META: Meta = Meta {
    id: "heat-explicit",
    title: "Explicit diffusion on a one-dimensional grid",
    params: &[
        Param::count("cells", 64.0, 8.0, 256.0),
        Param::new("r", 0.4, 0.05, 0.9, 0.01, ""),
    ],
    outputs: &[Output::field("u", Block::Out, 0)],
};

pub fn init(a: &mut Arena) -> Status {
    // Read `cells` and `r` from the params block; the caller has already written
    // the initial field into `state`. Return BadParameter rather than panicking.
}

pub fn step(a: &mut Arena) -> Status {
    // One FTCS update. Return Unstable the first time the norm grows past the
    // declared limit, so the figure can say so while still drawing the answer.
}
```

The build turns that into:

```
assets/data/solvers/heat-explicit/
├── kernel.wasm      # the artifact, for provenance and for a non-JS consumer
├── kernel.js        # generated: the manifest and the wasm as base64
├── manifest.json    # params, outputs, layout, capacity, statuses
├── selftest.json    # inputs and expected outputs from the native run
└── SHA256SUMS
```

`kernel.wasm` is shipped beside `kernel.js` even though the page uses the inlined
copy: it is the thing the digest names, and a reader can check the JS against it.

### Why the wasm is inlined, not fetched

The service worker keeps content-addressed assets across a deploy and deletes
everything else's cache on `activate`. `assets/data/` is not content-addressed, so a
fetched `kernel.wasm` would be fetched again after every deploy, and a runtime
`fetch` of a missing file is a failure the asset graph cannot see. Inlining removes
three failure modes at once — no second request, no MIME type, no 404 — and the
bytes travel with the module the figure already imports. The cost is 33% more bytes
on a 10 kB file. The bundle could be content-addressed instead, but that would make
every figure import a hashed name the build has to rewrite into page source, which
is a larger change than it buys.

The generated module uses top-level `await`, so it is a **value** by the time a
figure imports it:

```js
// assets/data/solvers/heat-explicit/kernel.js (generated)
import { define } from "../../../figures/kernel.js";
export default await define({ /* manifest */ }, "AGFzbQEAAAA…");
```

A figure then stays synchronous, and the loader's existing
`await import(...)` already waits for it. A wasm that fails to instantiate rejects
the import, and the loader's catch shows "Figure failed to load" instead of a blank
panel.

### The one rule a figure must not break

A kernel's output is **simulated**, not proved. `claim()` is for arithmetic the
figure itself prints and the CAS can check; a number that came out of a time step is
not that. The selftest is its check. A page must not print a kernel result as if it
were exact, and the figure must not `claim()` it.

## Build and vendor: the rule that changes

`scripts/build-solvers.sh` has three modes, and the split is the point:

| mode | needs | does |
|---|---|---|
| (none) | Rust + the wasm target | rebuilds `assets/data/solvers/` in place — the authoring step |
| `--check` | Rust + the wasm target | rebuilds into a temporary directory and diffs it against the committed tree — **CI's job** |
| `--verify` | nothing | checks every file against `SHA256SUMS` and the bundle's `bundle.json` — **the local gate** |

`scripts/check.sh` runs `--check` when `cargo` is on `PATH` and `--verify` otherwise,
so a contributor without Rust still has a complete gate and CI always has the
stronger one.

The CI job:

1. `cargo fmt --check`, `cargo clippy --locked -- -D warnings`, `cargo test --locked`
   on the host;
2. `cargo build --locked --release --target wasm32-unknown-unknown` once per kernel
   feature;
3. `scripts/build-solvers.sh --check`;
4. `node tools/dist/cli.js solvers` — loads each generated module in Node, replays
   `selftest.json`, checks the bundle has every entry its manifest names, and
   enforces the size budget (32 kB raw, 16 kB gzip per kernel).

The toolchain is pinned twice on purpose: `solvers/rust-toolchain.toml` is what a
person's `cargo` reads, and the workflow asks for the same channel and target
explicitly. A CI that quietly used a different compiler would produce a different
digest, and the check would fail for the wrong reason.

### The rule in `.github/AGENTS.md` this replaces

The current rule is right about what it was protecting:

> **CI installs no compiler for a vendored binary.** … Regenerating it is an
> authoring step on a machine with Rust and the `wasm32-unknown-unknown` target,
> never a job here — a CI that builds a binary the page ships would let the two
> disagree silently.

The replacement keeps the principle and reverses the conclusion:

> **CI builds a vendored binary only to prove it.** A job may rebuild it and fail if
> the bytes differ from the committed tree; it may not write what ships. The deploy
> reads the committed bytes, and the deploy job installs no compiler. A rebuild that
> differs is a red gate, which is the opposite of the silent disagreement the old
> rule feared.

That distinction — **build to compare, never to ship** — is the one sentence to
remember. It also means the digest check survives: `SHA256SUMS` is what a reader and
an offline clone can verify without a toolchain.

### Why byte equality is the check, and where it stops

For `ot-solve` the evidence above says the bytes are reproducible across directories
with a pinned compiler, so the gate can demand equality. For `otkd` it cannot: the
payloads come from SymPy, NumPy and SciPy, and a different BLAS or a different
Python patch level can change the last bit of a number. `otkd`'s rebuild check is
therefore **correctness, not bytes**:

- the committed bundle's `SHA256SUMS` is verified offline;
- its compiled kernels are run against the Python reference (its own
  `tests/test_wasm.py` already does this);
- a full rebuild is a separate job that runs when the path changes, and a numeric
  difference is a reviewable change rather than a drift failure.

That is not a weaker rule for its own sake. It is the strongest check each artifact
can support.

## What the research says

Five primary sources shaped the choices, and each one settles a question that would
otherwise be a preference:

| source | what it says | what it settles here |
|---|---|---|
| [The rustc book, `wasm32-unknown-unknown`](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html) | the target imports nothing from the host for std; `println!` does nothing, `std::fs` errors, `std::thread::spawn` panics; the target compiles with `-Cpanic=abort` by default | the kernel is a number cruncher, not a program: no printing, files, threads or clock. `panic=abort` is the target's own default, not a trick |
| [Rust and WebAssembly, JavaScript interoperation](https://rustwasm.github.io/book/reference/js-ffi.html) | exported functions "must operate only on primitive numeric types"; JS "can freely read and write" linear memory; going beyond numerics is where a bindgen framework starts | a numerical ABI needs no `wasm-bindgen`. Seven functions and one arena are the whole interface, and the seam is the one the book describes |
| [Rust and WebAssembly, shrinking `.wasm` size](https://rustwasm.github.io/book/reference/code-size.html) | LTO, `opt-level = 's'`/`'z'`, `wasm-opt`, avoiding panics and formatting; the default allocator costs about 10 kB | the fixed arena and the no-panic style are size decisions as much as design ones. `wasm-opt` stays out until a kernel misses the budget; it is a Binaryen dependency for 15–20% of 10 kB |
| [Reproducible Builds, Rust](https://reproducible-builds.org/docs/rust/) | reproducible by default when the toolchain is version-matched and paths are normalised; commit `Cargo.lock` and build with `--locked` | `rust-toolchain.toml`, a committed `Cargo.lock`, `--locked` in the build script, and the two-directory equality test |
| [The `wasm-bindgen` guide](https://rustwasm.github.io/wasm-bindgen/) | its purpose is idiomatic interop — strings, structs, JS objects, promises | not this interface. Adding it would add a CLI whose version must match the crate, for a boundary that is eight numbers wide |

**`no_std` was measured and declined.** A `no_std` kernel cannot call `f64::sqrt`
(it is not in `core`), so it needs `libm`; a std kernel using `sqrt`, `sin`, `exp`
and `ln_1p` compiled to 8.9 kB (4.0 kB gzip). The saving is small enough that the
dependency and the lost method are the worse trade. If a kernel ever exceeds the
16 kB gzip budget, the order is: `opt-level = 'z'`, then `wasm-opt -Oz`, then
`no_std`.

## The otkd move

### How the history arrives

```bash
git subtree add --prefix=solvers/otkd \
    https://github.com/leonpjvaughan/suspension-kinematics.git main
```

Subtree, not submodule: the history comes with the files, a clone needs no second
fetch, and `git log -- solvers/otkd` still answers. The archived repository remains
the record of the split; the subtree is where it continues.

### What changes

| | before | after |
|---|---|---|
| repository | `suspension-kinematics` | `solvers/otkd` in this one |
| CI | its own `tests.yml` + `release.yml` | one job in `verify.yml`, cheap unless `solvers/otkd/` changed |
| release | a tag, a wheel, a zip, a GitHub release | none: the commit is the provenance |
| version | `hatch-vcs` from the tag | frozen at `0.12.0`, bumped by hand when the maths changes |
| dependencies | its own `uv.lock` | its own `uv.lock` — **not** a root workspace member |
| the book's copy | downloaded zip, sha256 in a script | built from `solvers/otkd` by `scripts/build-otkd.sh` |

**Not a root workspace member** is the important one. `otkd` depends on NumPy,
SciPy, SymPy and Pydantic; making it a member of `tool.uv.workspace` would install
all of that for every contributor and every CI job that touches the site. As a
nested project with its own lock it is installed only by the job that rebuilds it:

```toml
# root pyproject.toml
[tool.uv.workspace]
members = ["engine"]   # solvers/otkd is deliberately not listed: a project of its own
```

**The CI job is cheap unless the path changed.** GitHub Actions filters at the
workflow trigger, not at a job, and this repository has one gate with one required
check name. So the job runs always but does the expensive work only when
`git diff --name-only` names `solvers/otkd/`, or when the branch is `main` (which
deploys). A skip prints why, like `preview` does, so "not run" is not read as
"passed".

**Freezing the version** removes `hatch-vcs`, `scripts/version.py`, the release
workflow and the tag scheme, and it is honest: the last release existed to cross a
repository boundary that no longer exists. The bundle already records the commit
and the compiler in `MANIFEST.json` and `provenance.json`, which is the provenance
that matters. `otkd --version` still answers; it answers `0.12.0`.

### The bundle

`scripts/build-otkd.sh` replaces `scripts/vendor-otkd.sh`. It writes the same tree
at `books/maths-applied/docs/assets/data/otkd/`, with the same `MANIFEST.json` and
`SHA256SUMS`, from the local source. The README in that directory changes from
"written by a download" to "written by a build", and keeps the rule: do not edit it.

The acceptance criterion for the move is **no numeric change**:

1. rebuild the bundle from the moved source with the locked dependencies;
2. diff it against the committed tree;
3. every difference must be metadata (`generator`, `git`, the version string);
4. a difference in `out.js` numbers or `kernel.wasm` bytes stops the move and is
   reviewed as a maths change, not a move.

That is the check that makes "the move did not change the answers" a fact rather
than a hope.

### What the move touches in the books

- Eight deep links to source files, four links to the repository itself (the book's
  home page, the colophon, §1.1 and the Review), and the two data READMEs — the
  addresses become `solvers/otkd/...` in this repository.
- `books/maths-applied/sources.yaml` names the new location and the commit.
- The prose keeps calling it "the package". That stays true: it is still a package.
  Only the addresses change.
- The quarter-car README's "from a checkout of `suspension-kinematics`" becomes the
  path in this repository.
- `engine/src/textbook/legal.py → SOFTWARE` gains `ot-solve` and its licence.

### Archiving

After the move lands and the site deploys: set `suspension-kinematics` to archived,
with a final README line pointing at `solvers/otkd`. Releases stay published, so an
old vendor pin still resolves; nothing in this repository uses them any more.

## Names and the namespace question

The honest answer is that **a registry namespace is not what this needs yet**. A
namespace is a distribution decision: it buys independent publication and a shared
import path for consumers outside the repository. There are none. Every kernel is
compiled here and served as a static file; nothing is installed from PyPI, npm or
crates.io.

| thing | name now | if published |
|---|---|---|
| repository | `Open.Textbook` | — |
| site | `open-textbook.org` | — |
| Python engine | distribution `textbook`, import `textbook` | `open-textbook-engine`, import unchanged |
| Python kernels | distribution `otkd`, import `otkd`, command `otkd` | `open-textbook-otkd`, import and command unchanged |
| Rust library | crate `ot-solve`, lib `ot_solve` | `open-textbook-solve` only if a second consumer appears |
| JS packages | none (the site ships files) | scope `@open-textbook`, e.g. `@open-textbook/kit` |
| binary ABI | `ot-kernel-1` | — |

Three reasons not to rename the Python import to `open_textbook.otkd` now:

- it breaks every `import otkd`, the console script, the docs and 110 tests for a
  package with one consumer;
- `docs/naming.md` in `otkd` already decided this, and added the rule: "Do not rename
  the import twice";
- a distribution name and an import name are allowed to differ, so the family name
  can arrive later without a code change.

The one thing worth doing now is reserving the names in prose and in `DECISIONS.md`,
so a future publication is a packaging change rather than a rename.

## Phases

Each phase is independently shippable and independently verifiable.

**Phase 0 — the decision.** This document, a `DECISIONS.md` entry, and the queue
items. No code.

**Phase 1 — `solvers/ot-solve`, one kernel, the build and the CI job.** No page yet.
Acceptance:

- `cargo test` proves the heat scheme against the sine-mode solution and the
  stability boundary;
- `scripts/build-solvers.sh --check` is byte-identical on a second run;
- `node tools/dist/cli.js solvers` replays the selftest and passes;
- the CI `solvers` job is under three minutes cold;
- `scripts/check.sh` passes with and without `cargo` on `PATH`.

**Phase 2 — one page runs it.** The parabolic page's `step-limit` figure is the
candidate: a static plot of `2N²` becomes a live scheme whose reader can push `r`
past `1/2` and watch it grow. That is a page decision, taken with the figure in
front of us, not assumed here. Acceptance: the figure audit in both schemes, the
phone floor, a Predict → Test → Explain wrapper, and no `claim()` on a simulated
number.

**Phase 3 — the otkd move.** Subtree, CI job, version freeze, bundle rebuild, link
rewrite, sources update. Acceptance: the no-numeric-change diff above, the book's
tests, and the archived repository pointing at the new path.

**Phase 4 — the next kernels.** `wave-explicit` (CFL, energy) and `poisson-cg`
(iteration count, residual history) when a page asks for them. Each is one Rust
module, one feature, one entry in the registry, one selftest — no new browser code.

**Phase 5 — archive.** After a deploy from `main`.

## Costs and risks

| | cost | mitigation |
|---|---|---|
| CI | a Rust job, ~1 min warm; an otkd job that is ~10+ min only when its path changed | cache `~/.cargo` and `solvers/target`; run otkd only when its paths change |
| contributors | Rust needed for `--check`, not for `--verify` | `check.sh` degrades to the digest check |
| repository | +1.4 MB of history, +~30 kB of committed wasm for three kernels | wasm is small; no LFS |
| coupling | a kernel change and the page that uses it can land in one commit | that is the point |
| reproducibility | a new compiler can change bytes | pinned toolchain; the bump is its own commit, and the diff is the evidence |
| otkd tests | 110 tests, ~2m15s for 21 | run only when the path changed; a session-scoped fixture is a separate improvement |
| the move | a bundle rebuild could change numbers | the no-numeric-change gate above |

## What this does not do

- Publish anything to npm, PyPI or crates.io.
- Put a Rust build in the deploy path.
- Add a bundler, `wasm-bindgen`, `wasm-pack` or `wasm-opt`.
- Move `books/maths-applied`'s model data into `assets/`: those models are that
  book's subject, not a shared kernel.
- Change the current `otkd` ABI in the same phase as the move. The move is a move.

## Decisions needed

1. **Layout:** `solvers/otkd` (recommended, one tree for both producers) or
   `packages/otkd` beside `solvers/`?
2. **The first kernel:** `heat-explicit` (recommended — it is the parabolic page's
   own subject, has an exact solution to test against, and its failure is the
   lesson), or `wave-explicit`?
3. **otkd version:** freeze at `0.12.0` (recommended) or keep a prefixed tag
   (`otkd-v0.12.0`) and a release train?
4. **Namespace:** confirm no registry namespace now, with the names reserved in
   `DECISIONS.md` (recommended), or rename to `open_textbook.*` while the move is
